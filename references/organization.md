# Native mailbox organization
Start from the user's actual labels, categories, folders, and inspectable rules. Reuse useful organization and propose a small scheme. Avoid imposing the author's labels or asking the user to choose a taxonomy before seeing a useful preview.

Use deterministic rules for stable patterns such as an exact service sender plus a recurring subject. Use the LLM for meaning, ambiguous asks, and exceptions. Native rules continue running without model calls after installation.

## Promote a pattern
1. Identify a recurring pattern from actual reviewed examples. Keep competing explanations and exceptions visible. A sender alone may mix notices, invoices, and support replies.
2. Invite “change my email butler” to begin an Organization Plan or Rule Plan. Show exact account, criteria, action, existing-rule interactions, examples/counterexamples, and reversal method. Prefer visible labeling/category assignment first. Moving out of Inbox requires an additional reviewed decision about visibility.
3. Inspect current native rules and their ordering where supported. A rule lifecycle must support inspecting criteria/actions, creation, exact-ID removal, and verification. If lifecycle support is incomplete, keep the plan uninstalled and explain the one missing capability. Do not substitute a plausible tool name or arbitrary API call through a read-only connector.
4. Apply the approved local plan with the guarded writer, then perform only the specifically approved mailbox operations through supported tools. Use canonical provider IDs; folder creation and message filing are separate operations. For Outlook, preserve unrelated existing categories when a setter replaces the whole category array.
5. Independently inspect the installed rule and preserve its exact remote identity in a private operation record. State any mismatch or missing verification. Native rules are canonical; a local plan and a successful API response alone are insufficient.
6. Treat backfilling old messages as a separate preview with exact frozen targets. A query-based bulk operation can include newly arriving messages after approval; use it only when the user approved that dynamic scope and the provider can honor it. Otherwise use explicit message/thread IDs.

## Review and reversal
Inspect a bounded sample of matches and missed exceptions in later reviews. Propose revisions through change mode rather than learning silent new rules. Deleting a rule stops future handling; it does not reverse prior filing. Never promise that restoring configuration undoes remote actions. Preserve legitimate message access and review source links when available.
